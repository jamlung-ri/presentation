01 · Context

Where things stand

This has been a four-month effort to replace PanelsAndForms.csv — the current flat, denormalized panel file — with a cleaner, part-based model. It moved from framework debates in the spring, through worked examples in early summer, to a two-day F2F this week that resolved most of the open design questions in a single sitting.

April through June was mostly two-person design sessions—chiefly Stan Huff and Rob McClure, joined progressively by Steven Wagers and Elizabeth Lumakovska—working through the core question/preamble/answer-list model, collection typing, versioning, and where LOINC's boundary with a “knowledge base” should sit. Many threads carried from call to call without closing. Day 1 of this week's F2F changed that: 22 discrete decisions resolved in roughly three hours, closing out most of what had been open since April. Day 2 (today) stress-tested that resolved design against real PanelsAndForms.csv rows rather than continuing to debate the framework, and closed with the group explicitly summarizing what had been decided before an extended lunch/activities break — the design conversation may resume in a future call rather than continuing later today.

02 · Resolved

What's decided

Grouped by topic. Each reflects the latest, most authoritative resolution across all eight sessions.

Question identity

mostly settled
  • A question's LOINC identity is preamble + issue (question stem) + bound answer list, combined from separate, independently-reusable LOINC Parts into one composite code.
  • Answer-list overrides are eliminated going forward — a different answer list means a different LOINC code, even with identical question text. Reverses long-standing practice.
  • Any variation in exact wording (word order, punctuation, capitalization) makes two questions different concepts — removes subjective “close enough” judgment calls.
  • A preamble only becomes its own Part when the source survey itself presents it as a separate element — never inferred from repeated lead-in text.

Collections (replacing “panel”)

mostly settled
  • “Collection” is the generalized replacement for “panel” — one typed construct covering lab panels and survey instruments alike. Only ~4–5 types expected.
  • Headers/subset-organizers are members of a collection, not a collection type — they get real codes but function as reference info, not answerable questions.
  • Organizers/groupers get real LOINC codes; purely descriptive content never meant to exist outside its parent collection gets LOINC Parts only.
  • Every survey has three code roles: the whole-instrument code, collection code(s) for question groupings, and a final score/result code.
  • Header codes are now reused across different assessments even when their contents differ underneath — e.g., one code for “Administrative Information” across multiple forms. Changed recently at CMS's request; confirmed live against real MDS data on Day 2, and is the first phase of a larger CMS cleanup — sub-panels are next.
  • A collector is permissive (a class/type declaration, no fixed membership) by default, unless explicitly marked rule-bound. Confirmed live against MDS Section GG, where question sets and even section presence genuinely vary across subsets. Proposed as a general rule beyond surveys, including lab — not yet discussed with the lab committee.
  • This is explicitly the same fix as eliminating answer-list overrides (see Question identity, above): overrides were always a workaround for not having a proper way to say “this can vary” — confirmed live that the current override mechanism already breaks this rule at the question level too, not just the collector level.

Versioning

settled
  • Meaning permanence is preserved: a materially-changed instrument gets an entirely new LOINC, never an in-place version bump. Precedent: lab's Basic Metabolic Panel 2007 vs. 2015 codes.
  • A survey collection is unique per version — any metadata change, not just the answer list, warrants a new code.
  • “Version” is reserved for the same survey changing over time via its authoritative source — genuinely different instruments (e.g., a child vs. teen-caregiver vs. teen-self-report form) are not “versions” of one survey.
  • A version-tracking group mechanism is planned so “find all versions of X” still works — mechanism itself not yet designed.
  • Not every collector carries a version: “version” only makes sense for content that's genuinely static. A permissive collector carries no version of its own (its content is scoped by LOINC's release cycle instead); only a rule-bound collector representing an externally-versioned object (e.g., CMS's MDS release) carries one, and LOINC holds that external version rather than assigning one.
  • For rule-bound collectors, changing the rule itself is grounds for a new concept — same change-management logic as changing content.

Screener interpretation & scoring

mostly settled
  • A screener has exactly one interpretation code, bound to a value set covering every possible outcome level — not one code per branch.
  • Sub-scores bind to the collection that produces them; a screener doesn't need one overall instrument score.
  • Skip logic is free text tied to a collection item, never an executable algorithm — a computable version was tried and abandoned.
  • LOINC does not compute or publish calculated scores — that's a downstream vendor's job (e.g., IQVIA administering and tabulating).

Metadata scope

boundary held, discomfort acknowledged
  • Litmus test: if someone unfamiliar with the survey needs it to understand a received value from the LOINC representation alone, it's “form context.” Pure how-to-fill-out-the-form direction is “form instructions.”
  • The team keeps capturing form context/instructions, Observation ID, cardinality, and skip-logic text — despite discomfort with LOINC acting like a knowledge base — because of CMS contractual obligation and tooling precedent.
  • Method is not populated on individual survey question codes — only at the panel/survey level and on score codes, to preserve question reuse.
  • Sharpened boundary: anything meaningful and exchangeable belongs in the LOINC tables; everything else is “questionable” and belongs in a knowledge base — except when a paying client (CMS) explicitly requires it, which LOINC will still do, but explicitly not as its own goal.
  • In progress, not fully closed: knowledge-base artifacts (instructions, skip logic, example text) should become identified objects in their own table, not anonymous embedded text — tied to the LOINC(s) they apply to, but without needing to encode exactly where they render on a form.
03 · Structure

The new model, shape

Two mechanisms replace what PanelsAndForms.csv does today with one flat, self-referential table: a linking table for membership, and part-composition for question identity.

What actually changes: if PHQ-4 were reused with a different answer scale (say, a 5-point instead of 4-point list), the current model would attach it via a second AnswerListIdOverride row on the same code, 69725-0. Under the resolved design, that's a different question — it mints a new LOINC, because the answer list is now part of what makes the code mean what it means.
Also changing for this same question, not shown above
  • Versioning: if PHQ-4 were revised, the revision gets an entirely new instrument code (69724-3 stays permanently tied to this exact version) — not a version-bumped variant of the same code.
  • Method: not populated on 69725-0 itself under the current convention either, but now explicitly documented as policy — Method lives at the panel/survey level and on score codes only.
  • Membership: ParentLoinc as a repeated column value on every child row is replaced by COLLECTION_ITEM as a proper linking table — still debated as of Day 2 vs. keeping parent-child as embedded columns.
05 · Boundaries

In & out of scope

What LOINC will represent for a survey, and what it deliberately leaves to downstream systems or a separate knowledge base.

In scope
  • Form context (preamble, look-back periods) — anything needed to understand a received value from LOINC alone
  • Form coding instructions
  • Observation ID (form-specific question numbering)
  • Required / optional / conditional flags (Gravity & CMS)
  • Question & answer cardinality
  • Skip logic, as reference text
  • Intended question sequence / order
  • Subset-organizer / header codes
  • A final score or interpretation code per screener
  • Target (who it's about) & administrator/reporter, as structured elements
Out of scope
  • Computing or publishing calculated scores — that's a downstream vendor's job
  • Proprietary scoring methodology behind an IP-controlled instrument
  • Executable branching / flow logic — CDS territory, not LOINC
  • Usage guidance (“who should use this,” “when”) — belongs in a separate knowledge base
  • Administration mode (phone vs. in-person) as a distinct survey code
  • Interpretive / eligibility framing text
  • Client-specific billing elements (e.g., CPT “cuts” data) in the public table
  • Curating/recommending which instrument to use — not competing with survey knowledge-base vendors
06 · Unresolved

Open issues

What's still genuinely undecided, most consequential first.

Design

Loose ends on the now-confirmed permissive-by-default rule

The permissive-vs-fixed tension itself is resolved (see “What's decided”): a collector is permissive by default unless explicitly marked rule-bound. Three real loose ends remain: the exact mechanism for a rule-bound collector's rules (“can be complex or simple” was said, nothing was specified) is undesigned; how the original motivating case for “fixed” — redundancy checking across overlapping lab orders (an ordered BMP and an ordered renal panel both include sodium, so it shouldn't be tested twice) — actually gets satisfied under this model wasn't revisited once the permissive framing won out; and the rule hasn't been socialized with the lab committee even though it's framed as applying beyond surveys.

Design

How much should FHIR shape the model?

Live disagreement as of Day 2: FHIR as a modeling pattern vs. FHIR as a reference point only (“it's a transmission syntax, not an information model”). Tabled — someone is to propose an approach and bring it back. Separately, FHIR R6's new Observation.organizer is treated as validating our existing direction, not a point of disagreement itself.

Design

Associative table vs. embedded parent-child columns

The COLLECTION_ITEM design assumes a separate linking table, but as of Day 2 this was still actively debated — some prefer embedding parent-child relationships as columns, closer to how ParentId works today.

Rule scope

Exact scope of the “exact wording” rule

Do capitalization, emphasis, and punctuation differences count as meaning-changing, not just word order? Flagged as needing broader stakeholder feedback before finalizing.

Mechanism

Groups vs. Ontology for linking related questions

Not resolved which mechanism recovers cross-variant analysis once wording/answer-list differences mint separate codes. The existing LOINC Group table (~9,000 groups) is considered messy and may need redesign; governance/ownership of Groups is undesigned either way.

Edge case

“Postamble” — mid-sentence question variation

The preamble/issue split assumes variation sits at a clean prefix boundary. Real examples exist where the differing text is embedded mid-sentence. Not covered by the current model.

Rule scope

CMS's header-alignment cleanup has a planned next phase

This release only cleaned up top-level section headers (removing embedded version numbers so they reuse across releases). Sub-panels and sub-sections still show the legacy pattern in places today (e.g., an embedded “1.18.11” visible mid-form) — CMS's next phase is expected to apply the same alignment there. Not yet scheduled.

Gap

Resident/administrative identifying fields aren't modeled

Surfaced live while walking MDS in the database: resident ID, assessment date, and who completed the form have no LOINC representation today. A real, unaddressed gap, not just a hypothetical.

Publishing

Panel structure isn't exposed in the public LOINC UI/search

Full membership data already exists internally, but today it's only reachable via the PanelsAndForms.csv download, not through search or the tree tool. Whether the new model changes this is unresolved.

Governance

IQVIA's score/total-code objection

Believed to be a misunderstanding — conflating the score value with a proprietary scoring algorithm — but deliberately not being resolved with IQVIA until after their contract is signed, to avoid the appearance of commercial influence.

Resourcing

Workstream is a persistent time drain against other priorities

Described on Day 2 as costing roughly 20% of time on an ongoing basis. Explicitly named as needing a decision from Marjorie. Separately, the group flagged that the regular weekly 1-hour call cadence “is not sufficient” going forward — calls may need to run longer.

Resourcing

No resourced time for Steven to build the actual database representation

Steven is named as having “a good understanding and functionality now” to do this, but the group closed the session without a time slot for him to do it, and flagged needing to find another resource without identifying one.
