00 · Orientation

The big picture

Two kinds of building block, and one linking mechanism, are all a survey is built from.

Everything in the new model is one of two things: a LOINC code (something that could plausibly show up on its own in an exchanged instance) or a LOINC Part (a reusable building block that only ever has meaning inside something larger). LOINC codes come in three flavors — Collections (survey instruments, sections, panels — anything that groups other things), Questions (built from Parts), and Score/interpretation codes. Everything nests via one mechanism: COLLECTION_ITEM, a linking table, not a self-referential column.

01 · Foundation

Parts vs. codes

The single question that decides everything else: would this ever need to stand alone in an exchanged instance?

Gets a LOINC code

If yes — it's exchangeable

Questions, Collections (survey instruments, sections, panels), and score/interpretation codes all get real LOINC identifiers, because a system receiving patient data might see any of them as the code on an observation.

Gets a LOINC Part

If no — it's a building block

A bare preamble, a bare issue/question-stem, collection instructions, reference text — none of these are ever the code on an observation by themselves. They exist to compose something that does get a code. Parts are reusable (the same preamble Part can pair with many different Issue Parts) but not independently exchangeable.

Example · real, from survey-concept-model-v2.md
Part LP900001-1 — “Over the last 2 weeks, how often have you been bothered by the following problems?”
never appears alone on an observation — only inside 69725-0, 68509-9, 44255-8, 44250-9
02 · Questions

Questions: preamble + issue + answer list

A question's identity is the combination of three Parts, not a single string.

LOINC code, composite

How it's represented

A question code is defined by exactly three things, each independently a Part: a preamble (shared context), an issue (the specific symptom/subject), and a bound answer list. Change any one of the three and it's a different question — a new code, not an edit.

Question = Preamble Part + Issue Part + Answer List (bound, not overridable)
Example · real data, PHQ-4 question 1
PieceValue
Preamble partLP900001-1 — “Over the last 2 weeks, how often have you been bothered by the following problems?”
Issue partLP900002-1 — “Feeling nervous, anxious, or on edge”
Answer listLL358-3 (NORMATIVE)
Composite code69725-0
Why a composite, not a single string: the same preamble pairs with different issues across PHQ-4's four questions (69725-0, 68509-9, 44255-8, 44250-9), and the same issue could in principle pair with a different preamble elsewhere — keeping the pieces as separate, reusable Parts is what makes both directions of reuse possible.
Two rules that follow from this

No overrides. Exact wording matters.

Because the answer list is part of a question's identity, there is no more AnswerListIdOverride — binding a different list means minting a different code. And because wording is part of the issue Part's identity, any variation — word order, punctuation, capitalization — makes a different question, removing the old subjective “close enough” judgment call.

Old · PanelsAndForms.csv
69725-0 reused; AnswerListIdOverride = LL358-3 attached per context.

A second context wanting a different list would override the same code again.

New · Composite identity
A different list means a different composite code — there's no code left to override.

Content is knowable directly from the code, every time.

03 · Collections

Collections: the generalized “panel”

One typed construct replaces panel, subset organizer, convenience grouper, and every other ad hoc grouping type.

LOINC code, typed

How it's represented

A Collection carries a type (survey instrument, lab panel — only ~4–5 types expected) and links to its members through COLLECTION_ITEM rows, matching a shared collection-link number — not a self-referential ParentId column the way PanelsAndForms.csv works today.

COLLECTION_ITEM: CollectionLoincNum → ItemLoincNum (item can be a Question, another Collection, a Header, or a score code)
The defining rule, confirmed 2026-08-26

Permissive by default; rule-bound only if marked

A Collection's membership is permissive (a class/type declaration — contents can genuinely vary) unless explicitly marked rule-bound (fixed or complex-rule content). This is a general rule, not survey-specific.

Example · real data, IRF-PAI Section GG

Section GG (“Functional Abilities and Goals”) is the exact pattern that motivated this rule: its parent/pooling structure repeats across assessment contexts (admission, discharge, different care settings) with genuinely different question sets and answer lists underneath — some contexts don't have the whole section at all. Real child rows from today's data:

LoincObservationIdInFormDisplayNameForForm
83218-8GG0170A3Roll left and right
83216-2GG0170B3Sit to lying
83278-2GG0170H3Does the patient walk?

A different assessment context (a different Collection using the same GG-series structure) can legitimately include a different subset of these — that's the permissive pattern, not a data-quality problem to fix.

Still open: the exact mechanism for a rule-bound Collection's rules ("simple or complex") isn't designed yet, and the case that originally motivated wanting fixed content — redundancy checking across overlapping lab orders — hasn't been revisited since the permissive default won out. Tracked internally as model-stress-tests.md, #1.
04 · Headers

Headers & subset organizers

Structural, not answerable — and now reused across contexts instead of re-coded each time.

Member of a Collection, not a type of its own

How it's represented

A header (e.g., “Administrative Information,” “Part 1”) gets a real LOINC code and is a member of its Collection — but it functions as reference info/coding instructions, not as something a user answers.

Example · real data — the exact old pattern being retired

Four real rows, all conceptually the same header (“Administrative Information”) on CMS's LCDS assessment family, each minted as a separate code because the version/context was folded into the component:

LoincComponent (as published)
85636-9LCDS v4.00 - Administrative information - admission
85663-3LCDS v3.00 - Administrative information - discharge
85673-2LCDS v4.00 - Administrative information - expired

This is precisely the pattern the header-reuse policy retires. Under the confirmed rule, “Administrative Information” would be one permissive header code, reused across admission/discharge/expired via COLLECTION_ITEM, with the version-specific content recorded per-instance rather than baked into three different component strings.

Why it was done the old way: two independent causes, both confirmed on 2026-08-26 — a technical constraint (LOINC doesn't allow duplicate Long Common Names) and a separate internal system policy against duplicate names in a table. Embedding the version into the component satisfied both, at the cost of fragmenting one concept into several codes.
Still open: this release only cleaned up top-level section headers this way. Sub-panels and sub-sections still show the legacy embedded-version pattern in places — CMS's next phase is expected to extend the cleanup there, not yet scheduled.
05 · Versioning

Versioning & meaning permanence

A code's meaning never changes underneath it. A new version is a new code — version lives beside the code, never inside it.

Core rule

How it's represented

When a survey instrument materially changes, it gets an entirely new LOINC code. Version is captured as its own database element, never embedded in the component or name. A collector code represents one specific external thing considered at one point in time — not a general, ever-shifting thing.

Identity = LOINC number alone — never number + version
Version = separate attribute, alongside the code, not inside its meaning
The cautionary case

What goes wrong without this rule

MDS 2.0 content could not be reused when MDS 3.0 was built, in real part because 2.0-era items had the version identifier embedded directly in the component itself — there was no clean way to say “this is the same underlying thing, just a newer release.” The LCDS example above (three codes for one conceptual header) is the same failure mode, caught on camera in current data.

Whose version is it: for CMS instruments, the version number is assigned by CMS, not by LOINC/Regenstrief — numbering can have gaps since it isn't the team's to control. If CMS wants to materially change core content, that's their job to issue as a new version, not LOINC's to accommodate by editing the existing code. This already matches how CMS operates, so it requires no additional training of CMS.
Not every collector gets a version at all

Version only applies to genuinely static content

“Version, by its very nature, is stating that content is static.” A permissive collector (see Collections, above) carries no version of its own — its content is scoped by LOINC's own publication/release cycle instead. Only a rule-bound collector representing an externally-versioned object (e.g., CMS's own MDS release) carries a version, and LOINC is holding that external version, not assigning one.

Permissive collector → no version of its own; content scoped by LOINC's release
Rule-bound collector → carries the version of the external object it represents
Rules can also change: for a rule-bound collector, changing the rule itself — not just the content — is grounds for a new concept: “if you have different rules, then that's a different concept... you change the rule, you got a new object.”
06 · Scoring

Scores & interpretation

Three code roles per survey. LOINC represents the outcome, never the algorithm.

Three roles, one survey

How it's represented

  • A code for the whole instrument (the top-level Collection)
  • Collection code(s) for groupings of questions
  • A final score/result or interpretation code

A screener gets exactly one interpretation code, bound to a value set covering every possible outcome level — never one code per branch. Sub-scores bind to the collection that produces them, so a screener doesn't need a single overall “instrument score” if only part of it produces a number.

Example · from the F2F Day 1 walkthrough — Expanded Food Security Screener

Collection 1 (yes/no items 1A/1B) and Collection 2 (scored items 2A–2F, summing to point ranges) sit inside one screener. Only Collection 2 produces a numeric sub-score. The screener's overall outcome is a single Priority Level interpretation code, bound to an answer list of levels A through E — not a total score, and not one code per possible path through the questions.

What LOINC doesn't do: compute or publish the calculated score itself — that's a downstream vendor's job (e.g., IQVIA administering and tabulating). LOINC provides the code for the resulting value, not the scoring methodology, especially for IP-controlled instruments.
Still open: whether interpretive/scoring context (e.g., point ranges like “0 to 1 points”) should be embedded in an interpretation code's answer strings, for traceability to the source worksheet — argued both ways, never resolved. Tracked internally as model-stress-tests.md, #12.
07 · Scope

Form context vs. form instructions

The litmus test that decides what metadata LOINC keeps capturing.

The test

How it's applied

If someone unfamiliar with the survey needs a piece of information, looking only at the LOINC representation, to fully understand a received value — it's form context. Pure how-to-fill-out-the-form direction, not needed to interpret a value once received, is a form (coding) instruction.

Example · real data — skip logic captured as text
GG0170H3 CodingInstructions:
“If 0, Skip to GG0170Q3. Does the patient use a wheelchair/scooter? If 2, Continue to GG0170I. Walk 10 feet.”

This is captured as reference text tied to the item, never as an executable rule — a computable version of skip logic was tried in the past (with a contact transcribed as “John Hosler”) and abandoned: “that was a misunderstanding... never representative of the computer.”

In progress, not fully closed

Instructions become identified objects, but not positioned ones

Instructions, skip logic, and example text should get their own identifier in a separate table — not anonymous embedded text the way they exist today (“they're just table and table entry… all non-identified”). They need to be tied to the LOINC(s) they apply to, but LOINC does not take on encoding exactly where they render on a form: “I do not think we have an obligation to make it clear where it appears on the form.”

Still open: flagged the same day as something the team needs to “finish and clarify” — proposed, not yet finalized.
In scope Out of scope

Where the line sits

  • In: form context/instructions, Observation ID, required/optional/conditional flags, cardinality, skip-logic text, question sequence, header/subset-organizer codes, one interpretation code per screener, Target & Administrator as structured elements
  • Out: computing/publishing scores, proprietary scoring methodology, executable branching logic, usage guidance (“who should use this”), administration mode as a distinct code, interpretive/eligibility framing text, client-specific billing elements in the public table, curating which instrument to use
08 · Method

The Method field

One small, easy-to-lose convention, made explicit.

Convention, not new structure

How it's applied

Method is not populated on individual survey question codes — only at the panel/survey level, and on score codes. This preserves question reuse: a question tied to a specific survey's Method couldn't be reused by a different survey using the same question.

Status: referenced as an existing but previously-undocumented decision. Tracked internally as a draft decision record — still needs confirmation of who decided it and when before promotion.

10 · Reference

Glossary

CollectionGeneralized replacement for “panel” — a typed grouping construct (survey instrument, lab panel, etc.)
Collection ItemA member of a Collection: a Question, a sub-Collection, a Header, or a score code
COLLECTION_ITEMThe linking table itself — a shared collection-link number, not a self-referential parent column
Preamble (Part)Shared lead-in text/context that modifies the meaning of the issue(s) that follow
Issue (Part)The specific symptom/condition/subject text within a question
LOINC PartA reusable, non-independently-exchangeable building block — only has meaning inside a composite code
Header / subset organizerA structural member of a Collection; gets a code but isn't itself answerable
Permissive collectorA Collection whose membership can vary release to release — the default, unless marked rule-bound
Rule-bound collectorA Collection with fixed or rule-governed membership — mechanism for authoring the rule is still undesigned
Survey interpretationThe single code representing a screener's overall outcome, not per-branch
Form contextMetadata needed to fully understand a received instance value from the LOINC representation alone
Form (coding) instructionsPure how-to-fill-out-the-form direction; distinct from form context
Answer list overrideThe now-eliminated practice of reusing a question code with a swapped-in answer list
Object identifierAn existing internal mechanism scoping how a given code is used in a specific place, separate from the code itself
