Core model

Three release states, running at once

Every month, multiple releases exist simultaneously, each in a different state. Only Authoring can span more than one release at a time.

Exactly one

Release

Being published — the technical work of assembly and going out the door (FHIR build, ETL, handoff to West Coast Informatics).

Exactly one

Validation

Artifacts being checked. Whole-release level, one release per month — not term-level QA.

Multiple, in parallel

Authoring

Active editorial work. Can span several future releases at once — not serial. This is what absorbs long-lead-time content (CMS, Gravity, large surveys).

Worked example
MonthReleasingValidatingAuthoring
This month2.842.852.86, 2.87, 2.88
Next month2.852.862.87, 2.88, 2.89 (new)
Month after2.862.872.88, 2.89, 2.90

When a release's content-freeze date arrives: if the targeted content is done, it moves to validation. If not, it gets pushed to a later release rather than holding everything up in place.

The working vocabulary

Steven: “These are the words we're going to use today.” Replaces looser prior usage (e.g. "QA" / "post-QA review").

TermDefinition
ReleaseThe continuous offering-through-QA lifecycle for a set of terms. Several releases can be open at once.
AuthoringBatch editorial work targeted at one specific release. Can span multiple months in parallel.
Content freezeA date, not a window — when authoring stops for a given release and it moves to validation.
ValidationChecking of release artifacts, whole-release level (one release, one month) — not term-level QA.
Release monthThe month the technical assembly/publishing work happens.
TaskA unit of editorial work assigned to a person, targeted at a release.
WorkspaceA sandbox attached to a task — edits land here first.
CutoverMoving work from workspace into QA to close the release — an end-of-month action.
QA reviewReplaces the old term "QA."

Validation month

Week by week

Validation spans a full month (vs. today's ~2 weeks) because authoring and publication for other releases run in parallel the whole time.

WeekFocus
Week 1Buffer to absorb any overrun from the prior release. Validation opens, assignments given out. Deliberately kept light.
Week 2Core validation work — environment, artifacts, etc.
Week 3Continued validation workflow — issues logged and addressed, closing out and signing off by end of week.
Week 4Freeze, publish, out the door. Handoff to West Coast Informatics (FHIR build), ETL to servers.

Urgent/critical late items: no dedicated lane in the model, but intended to have enough slack to absorb genuinely critical content unless a release is truly at the door. Decision: keep the existing "special use" tag mechanism specifically so urgent items don't have to break cadence.

Release calendar · decided live

The 15th of every month

Chosen as a fixed calendar date (like RxNorm), not an "Nth weekday" rule — the room valued predictability over dodging occasional weekend-adjacency.

Decided
MonthTreatment
DecemberFully skipped.
JulyDeliberately reduced scope around the 4th — not a full skip.
October / NovemberEarlier leaning was "shrink, don't skip" (conference in October; Thanksgiving in November; avoid two consecutive full skips) — not re-confirmed after the 15th-day decision. See Open items.

Right-sizing habit (new): when planning a month's authoring work, explicitly check which release month it lands in and size accordingly (e.g. "we're authoring 2.87 now, its release falls in October — that affects what goes in it").

Proposed · from Steven's deck, not yet confirmed live

Release operating cadence

A three-tier meeting structure so status isn't found by asking people one at a time. Each tier does exactly one job.

Proposal
TierWhenLengthWhoOutput
Release planningOnce/cycle, at scoping60–90 minContributors + stakeholdersCommitted work plan, named owners, dates
StandupTue / Wed / Thu20 minFull teamBlockers routed with an owner
Working sessionSame/next day, as needed30–45 minOnly those involvedA decision, an owner, a date

Core principle: the standup detects and routes blockers — it does not solve them. Problem-solving happens in the working session. And: the standup can only report against what planning committed; without planning, standup degrades into a status call.

What planning commits (the standup tracks against this)
CommitmentWhat that means
ScopeItemized per release, not described in aggregate
OwnersA named person per item — never a team
DatesA target date per item, not just the release cutoff
DependenciesIdentified and sequenced between items
RisksKnown risks, each with an owning person
The 20-minute standup script, same order every time
Segment~TimeCovers
Per release~4 minTerms passed/failed validation since last standup + top failure reason; at-risk-against-cutoff yes/no; blockers (what, who, needs which people)
Intake~4 minArrived since last standup; oldest open item age; count past target
Routing~4 minAnything escalating — every blocker leaves with an owner and a working-session slot

Rule of thumb: if an answer would take longer than one sentence, it goes to the parking lot instead of eating standup time.

What each meeting replaces
TodayUnder this cadence
Status found by asking individualsReported in a standing 20-minute slot
Scope committed informally, ownership implicitCommitted at planning, named owner per item
Intake worked when someone notices itReviewed three times a week
Blockers raised in 1:1s or not at allRouted to a working session with a date

Explicitly out of scope for this framework: governance, metrics, and the QA-gate conversation. Status: presented in Steven's deck; not yet confirmed as adopted in live discussion as of this update.

Risks

RiskDetailStatus
West Coast Informatics (WCI) integration time WCI's FHIR pipeline needs a full fresh export/re-ingest every single release, not incremental. Their first real run (turned on the day of this meeting) reportedly took several days. Clarified live: this build work happens after release lock, not before — WCI gets the full following month (15th to 15th) to build from a locked release, not a tight post-release window. Mostly resolved
Redundancy / bottleneck on single-owner content areas Elizabeth holds essentially all survey work with no backup — a real risk to authoring continuity if she's out. Precedent: a prior attempt to cross-train someone else (Felicia) onto CMS content was contractually forbidden by that work's funding contract. Not a training gap — a funding/contracting constraint ("our hands are tied"). Unresolved

Bonus insight from the WCI discussion: monthly cadence generally lowers the cost of late-breaking items — instead of an in-place fix/revalidation scramble, a late item just waits for next month's release (“you got 28 days, you can wait”).
