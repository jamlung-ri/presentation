Conflict detection across concurrent releases

The mechanism that makes Day 1's "multiple releases authoring in parallel" model actually work when the same record gets touched by more than one release cohort.

ItemDetail
Base data Every record in a workspace tracks a "base data" value — what that record looked like in production when you started editing it there.
Conflict trigger If production has since diverged from your recorded base data — someone else's change from an earlier release published in the meantime — and you've also modified that record, it's highlighted as a conflict to resolve.
Resolution options Accept the production version as correct (drop your workspace edit), or assert your workspace change is better and let it overwrite on publish.
Worked example A CMS-related record targeted for 2.86 gets edited in your workspace. Meanwhile 2.84/2.85 ship first and happen to touch the same record. When your 2.86 work later touches it, you get a conflict error — the base data moved out from under you.
Confirmed live You keep full editing capability regardless of what's on hold or not yet in production — the conflict flag is a signal to reconcile, not a block on working.

How tasks get created

Two distinct paths into a task, plus sizing and naming guidance.

Decided
ItemDetail
Reactive fixes A Help Scout inquiry ("these terms are wrong") becomes a standalone task — description of the needed change, targeted to a release, assigned to whoever can make it. Not tied to a formal "requested link" submission (that requirement is going away for this class of work).
Planned / submission-driven work Tasks tied to requested changes and submissions already in the pipeline get set up during the pipeline planning calls.
Sizing Keep tasks small and logically scoped — unless the content is genuinely one big logical unit (e.g. CMS). Example: ~50 allergy terms across 5 submissions can be one task ("allergy terms for 286"); the underlying items still belong to their individual submissions and route back there when done.
Mental model A task is an abstraction layer over the underlying submissions/requests — analogized live to a Git branch. Task-within-task nesting: just one level for now.
Naming Steven's strong preference: lead with an action verb, so the task name says what's being done, not just what it's about.

Target-release decisions become a group call

Deviating from a planned release target moves from an individual call to a group decision. Steven had the whole room explicitly acknowledge this rather than nod along.

Principle decided, mechanics open
ItemDetail
The change Previously, individuals could effectively commit release targets on their own — e.g. in stakeholder meetings (Wednesday afternoons with Stan called out specifically). Going forward, deviating from a planned target is a group decision.
Explicitly not prohibited Informing the group about individual work stays completely normal — e.g. "CMS work came in, I'll flag it at the next standup" needs no pre-approval.
Open question (unresolved) Exact order of operations: can you set a target release on something to avoid losing track of it, then bring it to the group afterward — or does the group need to sign off before the target is set? Posed live, not answered in this segment.
Also open How this applies to ad hoc/urgent items (e.g. an urgent request that Elizabeth picks up) — raised, cut off mid-example.

Two overhaul initiatives: database rebuild vs. request model

Directly follows from the domain-model discussion above — the foundational work that would be needed to support it.

ItemDetail
Database rebuild ("down to the studs") Rob's proposal: a full rebuild/decoupling of the database itself, not the application code or tooling layer.
Submission → request model Rework "submission" terminology/model into "requests" — a request better reflects something actually sent in by someone; also wants a clean split between genuinely new content and revised content, rather than folding new content in as "revised."
Sequencing Debated, not resolved: doing the request/submission overhaul first risks revisiting it once the database rework lands. Alternative: decouple the two efforts so they run in parallel instead of one blocking the other.
Why the database work is hard Substantial business logic lives directly in the database today — stored procedures, not application code — tightly coupled to specific tables and fields (Radiology and Document Ontology given as concrete examples). This coupling is a major obstacle to cleanly building out workspaces and decoupled architecture, directly relevant to today's workspace/conflict-detection demo.
Guiding philosophy Steven: "the database should just be a database, not a program." Internal/business logic in the data layer needs to be decoupled and pulled out.
Confirmed: two parallel initiatives (1) Decouple business logic out of the database. (2) Overhaul requests/submissions, decoupled from the terminology database. Confirmed these can run in parallel rather than needing to be serialized.
Capacity concern Raised, not resolved: the team already has a lot in flight (the monthly-release transition itself). Idea floated: draw on AI budget for this kind of internal-process work, not just content work. "We just got to figure that out."
Where does this get tracked? Decided: Steven will create a "strategic priorities" project in Basecamp. Explicit worry that drove it: "I don't want it to live in a parking lot and get lost forever." The two initiatives go in as tasks with check-ins for now, refined as next steps get figured out.

Pre-work required ahead of the planning call

Decided
ItemDetail
The requirement Terminologists/developers evaluate their own current state ahead of the call — what they have, what packages/tasks they're likely to work on — so they arrive with priority-based thinking already done.
Timing & budget Happens before the call, not during it. About one hour budgeted for the evaluation.
Process Each person evaluates independently, brings their own proposal into the call, and it's checked against agreed criteria as a group — ties directly into the group-decision governance change above.
Task-building during pre-work Fine to build draft tasks and group related items (e.g. bundling related submissions into one task) without targeting a release yet — targeting happens at or after the planning call.
